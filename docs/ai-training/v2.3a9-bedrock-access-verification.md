## 3. Two separate, independently-confirmed problems (not collapsed into one)

### 3a. Lambda execution role: IAM policy gap for the API the code actually calls

The role's inline policy (`fitness-assistant-dev-ai-runtime-policy`)
declares `bedrock:InvokeModel` — and only that action — scoped exactly
to the Nova Pro apac inference profile (plus a conditioned
foundation-model ARN and a separate Cohere-embedding statement).
`iam:SimulatePrincipalPolicy` against this exact role and exact resource
confirms: `bedrock:InvokeModel` → **allowed**;
`bedrock:InvokeModelWithResponseStream`, `bedrock:Converse`,
`bedrock:ConverseStream` → **implicitDeny**. Production code
(`backend/services/ai-service/src/llm/bedrock.client.ts`) calls the
**Converse API** (`ConverseCommand`), not the legacy Invoke API — so
even if the account-level block in §3b were resolved, the Lambda's own
role, as currently written, would still be denied for the exact call
the code makes. This is a genuine, concrete, independently-discovered
IAM-policy gap — not fixed, per explicit instruction (`IAC changed = NO`).

### 3b. Account/profile-level validation block — reproduced fresh, affects full-admin identity too

Two independent smoke requests were sent against the exact configured
model, with no substitution: a `ConverseCommand` and, as a targeted
diagnostic (not a retry, not a workaround), an `InvokeModelCommand` —
both using the **local admin identity**, which has unrestricted
`bedrock:*` IAM access and therefore cannot be blocked by §3a's gap.
**Both returned the identical error**: `ValidationException`, HTTP 400,
`"Operation not allowed"` (request IDs `d74825e6-...` and
`a687d8a6-...`). Because this reproduces identically regardless of
which Bedrock Runtime API is used, and under an identity with full IAM
Bedrock access, it rules out an IAM-permission cause for this specific
error and points to an **account/profile-level Bedrock entitlement or
validation restriction** on `apac.amazon.nova-pro-v1:0` for this
account — separate from, and in addition to, §3a's role-policy gap.

Per the task's own explicit error-classification rule (never collapse
every failure into "Bedrock closed"): this is precisely
**`BEDROCK_OPERATION_NOT_ALLOWED`** — the exact error name/message
match. No retry was attempted (`ValidationException`/"Operation not
allowed" are explicitly on the non-transient, do-not-retry list); the
second smoke request served diagnostic isolation, not brute-force
retry.
